## System overview
`src/azure_tenant_audit/` is the Microsoft 365 engine: collectors and adapters read the tenant through the guarded Graph and PowerShell paths, `normalize` and `findings` build evidence, `value_rules/` answers the 102 SCuBA policies, `explainer/` renders the deterministic template, `output_redaction` applies the redaction profiles and `finalize` seals a validated run bundle. It never imports `auditex`.
`src/auditex/` is the product layer: the `auditex` CLI and guided flows, reporting, exporters, compare and drift, customer packs, the Google Workspace provider and the local MCP server; it calls the engine and reads bundles.
Configs, schemas and profiles under `configs/`, `schemas/` and `profiles/` drive collection scope and contracts; shipped content is listed in both `pyproject.toml` data-files and `shipped_content.py`.
Gates are local only (no hosted CI): `make lint`, `make test`, `make contract-smoke`, `make release-check`, `make audit-deps`, `make dist` with the release smoke and `scripts/check-reproducible-build.py`; plan v3 adds Ruff to `make lint` (M00) and a `make acceptance` target (M01).
The parked model layer is retired in M02 (v2 DEC-004) after its shared helpers move to non-model homes; `tenant-bootstrap/` is lab tooling with writable operations whose `azure_tenant_audit/` package forwards to `src/`.

Test files: a module owns the test globs in its row. Any other `tests/test_*.py` belongs to the module whose code it imports first (engine before product), and the task that changes it names it on its `files:` line. Two tasks never share a file at the same time, whatever the module. New files (for example `benchmarks/html_peak.py`, `tests/test_tenant_bootstrap_forwarder.py`) fall under the row whose glob matches them; a new path no row matches needs a map edit before it lands.

## Interfaces
- Engine to product: `azure_tenant_audit` public functions and the run-bundle layout in `docs/reference/output-contract.md`; `CONTRACT_VERSION` in `src/azure_tenant_audit/contracts.py` changes only with a DECISIONS.md entry and an output-contract date change.
- Value rules to everything else: `configs/scuba-value-rules.json` (spec v3.9.1) and the rule registry in `value_rules/__init__.py`; the explainer reads catalogue cells only and never changes a verdict. Retiring the model layer must not change any verdict, explainer output or bundle field; `scripts/compare-run-outputs.py` against `tests/fixtures/contract-smoke-digests.json` (M02-T02) proves it, and a needed change stops the work for a G re-baseline.
- Shared helpers leaving the model layer (M02-T01 fixes the names before M02-T03 or M02-T04 starts): explainer derivation and validation and its schema table from `model_assessment.py`, `NOT_COLLECTED` from `model_evidence.py`, and the two `model_eval.py` helpers used by reporting, projection, export and value rules.
- Redaction: `secret_hygiene.redact_argv` with each parser's sensitive-flag set (`command_runner.SENSITIVE_ARGS`, the Google `run._SENSITIVE_COMMAND_FLAGS`, `secret_hygiene.SENSITIVE_ARG_FLAGS`, `auth_runtime.SENSITIVE_CLI_ARGS`); D3 profiles and the D5 person-name pass via `output_redaction` only (M05-T01 fixes the D5 entry points and the pseudonym helper before M05-T03).
- Transport policy (classes from plan v2, unchanged except class 6): (1) tenant read: GET through `graph._request` and the read guard, or a GET to the Power BI, Power Platform or Teams admin REST APIs, and the Google Workspace read APIs; (2) token: Entra and Google OAuth token endpoint POSTs; (3) Graph `$batch` POST whose sub-requests are all GET; (4) public lookup: DNS-over-HTTPS and exposure GETs; (5) operator-configured outbound sink: Teams and Slack webhooks, Jira and GitHub issue POSTs, SMTP, opt-in, redacted, never to the tenant; (6) parked model endpoint: removed by M02-T04, after which any such site fails the allow-list test; (7) lab-only response path behind `AUDITEX_ENABLE_RESPONSE`; (8) local subprocess: sign-in CLIs, PowerShell with read-allow-listed cmdlets only, the probe and local system tools. A site outside these classes needs sol and, for a product question, G before it lands.
- Read boundaries: no collector requests message, mail, file or attachment content; PowerShell cmdlets come only from the `api_inventory` read allow-list; Google calls are read methods under read-only or metadata-only scopes, with the four documented write-capable scope exceptions (v2 DEC-010).
- MCP: tool names, arguments and `read_only_hint` in `mcp_registry.py`; path arguments confined by `mcp_paths.py` to `AUDITEX_MCP_ROOT`.

## Conventions
Python 3.11+, `.venv/bin/python`; pytest with `pythonpath = src`; tests in `tests/test_<area>_*.py`, fixtures under `tests/fixtures/`, auth and secret paths behind `tests/conftest.py`; Ruff (pinned to the pre-commit hook version, with the hook's rule set E4, E7, E9, F and its target version) through `make lint` from M00.
CLI parsers use `allow_abbrev=False`; every secret-carrying flag sits in its redaction set with an abbreviation and a redaction test.
Feature flags are environment variables read in `src/auditex/features.py` (`AUDITEX_ENABLE_RESPONSE` lab only).
Shipped content changes update `pyproject.toml` data-files and `shipped_content.py` together; rule changes rerun `scripts/generate-rule-packs.py`. Removals go through the deletion gate: G approves the exact path list first; the orchestrator then writes one `.plan/CLEANUP.md` row per approved path (`| \`path\` | reason | evidence | DEC-nnn | |`, no `|` inside cells) and fills the commit column after the merge. A removal task deletes exactly the rows carrying its gate's DEC id.
Commits signed, gitleaks-clean, one coherent change each, staged by pathspec; no workstation paths, credentials, live evidence or sealed evaluation rows in the public repo.

### Plan v3 evidence rules
- Under `.plan/work/` only `result.md` files and `PLAN-*/*.md` are tracked; other work files (design notes, removal lists, logs) exist only in the main checkout. Durable facts a predicate reads live in tracked files: `.plan/DECISIONS.md`, `.plan/CLEANUP.md`, `.plan/work/ledger.tsv`, `result.md` files or repository files.
- Plan v2 used the same task ids M00-M03, so `.plan/work/<id>/` and `.plan/work/REV-<id>/` may hold plan v2 files. No predicate trusts such a path alone; it binds to a plan v3 merge (after tag `v1.3.0`) or a v3 DEC entry.
- Tier A review binding, for task `T`: the squash merge of `T` on `main` after `v1.3.0` carries the `Plan-Review: REV-T approve <sha>` trailer, and `REV-T/result.md` approves that exact sha (merge.sh writes the first 12 characters; the review's 40-character `reviewed:` line must start with them, shell-checked):
  `c=$(git log v1.3.0..HEAD --format=%H -1 --grep="^Plan-Task: $T\$") && test -n "$c" && s=$(git log -1 --format=%B "$c" | sed -n "s/^Plan-Review: REV-$T approve \([0-9a-f]\{12,40\}\)\$/\1/p") && test -n "$s" && grep -q "^reviewed: $s" ".plan/work/REV-$T/result.md" && grep -q '^verdict: approve' ".plan/work/REV-$T/result.md"`
- Provider binding (an orchestrator "Review:" item, not a shell predicate): the ledger has no reviewed-SHA column and v3 task ids repeat v2 ids, so no ledger query can tie a launcher to one review. At milestone close the orchestrator checks that the `sha` in the squash commit's `Plan-Review: REV-<task> approve <sha>` trailer prefixes the full 40-character `reviewed:` SHA in the review result, and that the review's dispatch record names a launcher of the other vendor from the author's. Each milestone Review item repeats this as an orchestrator check.
- Deletion-gate lists: `d=$(sed -n 's/^## \(DEC-[0-9]*\) <gate title>.*/\1/p' .plan/DECISIONS.md) && test -n "$d" && P=$(awk -F'|' -v d="$d" '{gsub(/[ `]/,"",$2); gsub(/ /,"",$5)} $5==d {print $2}' .plan/CLEANUP.md) && test -n "$P"` yields the approved paths; the DoD checks use `$P`.
