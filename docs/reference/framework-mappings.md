# Framework Mappings

Auditex maps each finding rule to controls in the security frameworks below. These mappings
appear in each finding's `framework_mappings` object, in the SARIF, OSCAL, and CSV exports, and
in the `baseline_alignment` section of `reports/report-pack.json`.

The mapping data lives in three files:

- `configs/control-mappings.json` maps each rule id to its framework controls.
- `configs/framework-catalog.json` lists, for each framework key, the source version, the
  publication date, the URLs used for verification, and the control ids Auditex may use.
- `configs/rule-packs.json` groups rules into packs by product area and by framework. It is
  generated by `scripts/generate-rule-packs.py`.

## Why `cis_m365_v3` was retired

The earlier `cis_m365_v3` values could not be verified. Several were wrong. For example, SPF,
DKIM, and DMARC were mapped to `4.4`, `4.5`, and `4.6`, but section 4 covers Intune. Every
diagnostic rule claimed `1.1.1`. The Intune rules pointed at `8.5.x`, which covers Teams
meetings. CIS now lists only version 7.0.0 as supported, and v3 numbers cannot be converted to
v7 numbers mechanically.

Auditex therefore switched to `cis_m365_v7` and kept `cis_m365_v3` only as a deprecated key. The
bundle validator still accepts it, so older bundles and operator overrides stay valid. Shipped
mappings must not emit it, and `tests/test_finding_templates_complete.py` enforces that.

## Mapping method

1. Map a control only when the rule's evidence tests the condition that control describes.
   Events such as risky sign-ins and privilege changes are not configuration controls, so they
   map to detection controls (`mcsb` `LT-2`, Zero Trust `secops`) and not to CIS or SCuBA
   configuration items.
2. Use ids listed for that key in `configs/framework-catalog.json`. To use a new id, verify it
   against the source first and add it to the catalog with a short paraphrased title.
3. Leave a framework out when no verified control fits. An empty mapping is better than a guess.
4. Diagnostic and coverage rules (`collector.issue.*`, `coverage.gap`, `service_health.*`) do
   not claim benchmark controls.
5. Every rule still needs `nist_800_53` or `iso_27001`, as before.

## Baseline alignment

`baseline_alignment.frameworks.<key>.controls` has one row per control that a shipped rule, or a
finding's own mappings, touches. Each row has a status:

- `fail`: at least one mapped rule has an open finding.
- `accepted_risk`: the only findings for the mapped rules are waived.
- `pass`: every mapped rule was evaluated and produced no finding. A rule counts as evaluated
  only when every collector that feeds it reached a `complete_*` coverage status and the
  evidence it reads was present.
- `not_assessed`: everything else, including blocked, partial, or skipped collectors and rules
  whose inputs were missing. Absence of a finding is never treated as a pass on its own.

Each entry in a control's `rule_statuses` carries `rule_id`, `status`, and `evaluated`. A rule that
was not evaluated also has a `reason`:

- `collector_not_complete:<collectors>`: a collector that feeds the rule did not complete. Most
  rules need `complete_*`; `identity.privileged_mfa_not_registered` also accepts a
  `not_applicable` `identity_governance` (no PIM data can exist), but not a blocked, partial,
  failed or missing one.
- `no_collector_mapping`: the rule's namespace is not in the collector map.
- `inputs_not_available`: the report was built without the normalized snapshot, so the rule's
  inputs could not be checked.
- `no_domain_records`, `resolver_error`: DNS rules need every verified domain resolved.
- `mta_sts_policy_not_fetched`: the MTA-STS policy rules need the policy file fetched (public
  lookups off, or the fetch skipped).
- `tls_rpt_not_collected`: the bundle predates TLS-RPT collection.
- `public_footprint_not_collected`: the public footprint rule needs footprint records.
- `signal_unknown:<reason>`, `signal_not_collected`: a detection rule needs its detection signal
  to be `on` or `off`, not `unknown`.
- `verdict_unknown:<control>`, `verdict_not_collected:<control>`: a rule decided by an identity
  control verdict (`ca.*`, `consent_policy.user_consent_*`) needs that verdict record to exist and
  not be `unknown`. `ca.enforcement_unverified` needs both the `effective_mfa` and
  `legacy_authentication_block` verdicts.

`baseline_alignment.frameworks.cyber_essentials` has a different shape: one row per catalogued
requirement, including those no rule maps to. See [Cyber Essentials](#cyber-essentials).

`baseline_alignment.unmapped_findings` counts findings that carry no `rule_id` (`count`,
`open_count`, `accepted_count`, `collectors` as a list of `{collector, count}`, and up to 20 `finding_ids`). They cannot reach a
control row. Every finding this version emits carries a `rule_id`, so `count` is 0 for these bundles;
a non-zero count means a bundle from an earlier version or imported findings, whose open findings are
in no control row, so check this bucket before quoting a roll-up from such a bundle.

`src/azure_tenant_audit/baselines.py` links each rule to its evidence collectors: `_RULE_COLLECTORS`
for rules that read from specific collectors (every collector listed must complete: the detection
rules, `attack_path.no_mfa_to_tier0`, the Global Administrator and privileged MFA registration
rules, which also need role assignments from `identity`) and `_NAMESPACE_COLLECTORS` for the rest
(`ca` maps to `conditional_access`). A rule that appears in neither reports `not_assessed` unless
it fails. A finding that is gone from a later run counts as resolved in `gate-drift` and
`compare` only if its own collector and every collector its rule needs completed there.

## Secure Score reconciliation

The defender collector reads `/security/secureScores` and `/security/secureScoreControlProfiles`.
Normalization keeps each snapshot's `controlScores` and the control profiles' maximum scores.
For every control profile id mapped under `ms_secure_score`, the report shows Microsoft's score,
the maximum score, and a `microsoft_state` (`implemented`, `partial`, `not_implemented`, or
`no_data`). It compares that with Auditex's open findings for the mapped rules:

- `agrees`: both sources report a gap, or neither does.
- `auditex_only`: Auditex has an open finding but Microsoft scores the control as fully
  implemented. Review the finding evidence. Microsoft's score may lag, or it may measure a
  narrower condition.
- `microsoft_only`: Microsoft reports a gap that Auditex did not flag. The rule may not have
  been assessed in this run.
- `no_microsoft_data`: the snapshot has no score for that control.

The `secure_score.low_overall` rule raises a finding when the latest snapshot's
`currentScore / maxScore` is below 50%.

## Mapping a new rule

1. Add the template to `configs/finding-templates.json` and the mapping to
   `configs/control-mappings.json`. Include `nist_800_53` or `iso_27001`, plus any verified
   benchmark controls. Do not add `cis_m365_v3`.
2. If a benchmark id is not yet in `configs/framework-catalog.json`, verify it against the source
   and add it there. For a Cyber Essentials requirement, add the id to the rule's `cyber_essentials`
   list and declare its `full` or `partial` confidence in `_cyber_essentials_confidence`; Google
   Workspace rules carry the id in `src/auditex/google_workspace/findings.py` and are listed in the
   same confidence table.
3. Add the rule's namespace to `_NAMESPACE_COLLECTORS` in
   `src/azure_tenant_audit/baselines.py` so a clean run can report `pass`. If the rule reads from a
   different collector than its namespace, or needs input that may be absent, add it to
   `_RULE_COLLECTORS` and give it an input check, so it reports `not_assessed` instead of `pass`
   when the evidence was not there. If the rule maps to a
   new product family, add it to `_M365_PRODUCT_FAMILIES` in `src/auditex/rules.py`.
4. Run `python3 scripts/generate-rule-packs.py` to refresh `configs/rule-packs.json`.
5. If the rule has a verified CIS v7 or Secure Score control, add it to the expected sets in
   `tests/test_framework_baselines.py`, then run the test suite.

Suggested starting points for rule families being added:

- `identity.stale_*` (inactive accounts): `mcsb` `PA-3` and `PA-4`, Zero Trust `identities`. CIS
  v7 and SCuBA have no automated stale-account item, so leave them out unless one is verified.
- `dns_posture.mta_sts_*`: no CIS v7, SCuBA, or Secure Score control in the verified set. Use
  NIST, ISO, and ATT&CK only. Zero Trust `data` is optional.
- `detection.*`: `mcsb` `LT-1`, `LT-2`, or `LT-3` (`LT-3` must be added to the catalog first)
  and Zero Trust `secops`. Do not map to CIS or SCuBA configuration items.
- `attack_path.*`: these composite findings inherit context from their member findings. Map
  only the Zero Trust pillar or pillars involved and leave benchmark controls to the member
  rules.

## Identity control verdicts

`ca.mfa_not_enforced`, `ca.legacy_auth_not_blocked` and `consent_policy.user_consent_unrestricted`
read `normalized/identity_control_verdicts.json` (see `docs/reference/output-contract.md`), not a
collector's raw rows. Each verdict is three-valued. A negative verdict raises the rule. An `unknown`
verdict, caused by a blocked, truncated or missing policy read, raises the matching diagnostic rule
(`ca.enforcement_unverified`, `consent_policy.user_consent_unverified`) instead. Those two rules
claim no benchmark control, so an unreadable policy list is neither a pass nor a failure.

- `ca.mfa_not_enforced` maps to CIS v7 `5.2.2.2` and SCuBA `MS.AAD.3.2v1` (MFA for all users).
  It does not map to `5.2.2.1`: an administrator-only policy satisfies that control while the
  rule still fires. `identity.privileged_mfa_not_registered` carries the same mapping as
  `identity.global_admin_mfa_not_registered`.
- `ca.legacy_auth_not_blocked` maps to CIS v7 `5.2.2.3`, SCuBA `MS.AAD.1.1v1` and Secure Score
  `BlockLegacyAuthentication`. The catalog entries were verified on 2026-10-20 against the Tenable
  CIS v7.0.0 audit list, the ScubaGear v1.8.0 `aad.md` baseline and the CIPP Secure Score profile
  sample already listed as sources.
- `ca.*` maps to the `conditional_access` collector and `consent_policy.*` to `consent_policy`
  (`_NAMESPACE_COLLECTORS`). Baseline alignment also reads the verdict records, so a rule passes
  only when its verdict is known: `enforced` or `not_enforced`, `blocked` or `not_blocked`,
  `restricted` or `unrestricted`. An `unknown` or missing verdict reports `not_assessed` with
  `verdict_unknown:<control>` or `verdict_not_collected:<control>`, never `pass`.

## Administrator set and count thresholds

Every `identity.global_admin_*` rule, `identity.privileged_mfa_not_registered`,
`identity.privileged_stale_account`, `identity.guest_with_privileged_role`,
`identity.admin_holds_productivity_licence` and the `attack_path.no_mfa_to_tier0` check read the
effective administrator set (`normalized/effective_admin_set.json`, see
`docs/reference/output-contract.md`), not the raw role assignments. The set counts each user once,
whether the role is direct, PIM-eligible or inherited through a role-assignable group, which is the
way the SCuBA `MS.AAD.7.1v1` instructions say to count, with one gap: PIM for Groups eligible
membership of a role-assignable group is not read, so a user who is only eligible to join such a
group is not in the set (ScubaGear counts them; the follow-up is in the changelog). Groups and service
principals that hold a role are listed but not counted.

When a source of the set was blocked, truncated or not run, the set is `unknown`. A skipped
`identity_governance` collector counts as blocked: the run cannot tell a missing licence from a
permission block or a failure, so only a `license_required` refusal on the PIM schedule read itself
means the tenant has no schedules. The rules that
depend on it then report `not_assessed` with `admin_set_unknown:<reasons>` when they find nothing,
`identity.global_admin_singleton` is not raised (a count of one proves nothing), and the diagnostic
`identity.admin_set_unverified` is raised. That rule claims no benchmark control. A finding the rules
can already make from what was read, such as a disabled administrator, still fails its rule.

CIS `1.1.3` and SCuBA `MS.AAD.7.1v1` give different ranges, so the rules compare the count with
each framework's own bound, kept in `_rule_thresholds` in `configs/control-mappings.json`:

| Framework | Control | Allowed Global Administrators |
| --- | --- | --- |
| `cis_m365_v7` | `1.1.3` | 2 to 4 |
| `cisa_scuba` | `MS.AAD.7.1v1` | 2 to 8 |

`identity.global_admin_sprawl` is raised above the strictest bound (more than 4) and states each
bound in `framework_thresholds`, with `breached` set per framework. Five to eight Global
Administrators therefore raise a `low` finding that fails CIS `1.1.3` while SCuBA `MS.AAD.7.1v1` still
reads `pass`; nine or more raise a `medium` finding that fails both. Baseline alignment reads each
framework against its own entry, and a framework with no entry (Zero Trust, MCSB, Secure Score,
Cyber Essentials) takes the finding as it is. `identity.global_admin_singleton` carries the same list
for the minimum of two. A test keeps the bounds, the catalog titles and each rule's mapping in step.

`MS.AAD.7.2v1` is a ratio (Global Administrators to other highly privileged users), which a count
cannot establish, so no count rule maps to it any more.

New rules:

- `identity.admin_holds_productivity_licence`: an administrator user whose licences, read by the
  licensing collector, include an Exchange Online mailbox or a productivity plan (Microsoft 365
  Apps, SharePoint, Teams). It maps to CIS `1.1.4` and, as partial evidence only, to the Cyber
  Essentials requirement `ce.uac.separate_admin_accounts`, whose status stays `ce_plus_assessor_test`.
  It needs the `licensing` collector and a licence list read in full, otherwise it reads
  `not_assessed`.
- `identity.stale_guest`: an enabled guest with no successful sign-in for `AUDITEX_STALE_GUEST_DAYS`
  days (default 90) while `signInActivity` was collected; `build_findings(stale_guest_days=...)`
  overrides it. A tenant without sign-in data reads `not_assessed` (`signin_activity_unavailable`). It
  maps to the Zero Trust `identities` pillar, MCSB `PA-3` and, as partial evidence, `ce.uac.remove_unused_accounts`;
  CIS v7 and SCuBA have no stale-guest control. A stale guest is reported by this rule only, not also
  by `identity.stale_enabled_account`; a guest that is also an administrator is reported by
  `identity.privileged_stale_account`.
- `identity.guest_with_privileged_role`: a guest that holds an administrator role by any route. It maps
  to MCSB `PA-1` and `PA-7`, Zero Trust `identities` and `ce.uac.special_access_privileges` (partial).

## Cyber Essentials

The `cyber_essentials` key follows **Cyber Essentials: Requirements for IT Infrastructure v3.3**
(NCSC, April 2026, listed as current on 2026-10-20). IASME applies v3.3 and the Danzell question set
to assessment accounts created after 26 April 2026 (its November 2025 notice says 27 April).
Accounts created earlier keep v3.2 for six months, so both versions are still in use until late
October 2026. The Cyber Essentials Plus Test Specification is still v3.2 (28 April 2025); there is no
v3.3 test specification. The catalog entry records the title, version, dates and URLs. The NCSC
documents are Crown copyright and are reused under the
[Open Government Licence v3.0](https://www.nationalarchives.gov.uk/doc/open-government-licence/version/3/),
as the [NCSC terms](https://www.ncsc.gov.uk/section/about-this-website/terms-and-conditions) allow, with
this acknowledgement: Auditex cites their headings and test-case names and copies no document text. The
IASME notices are cited for dates only.

**Method.** The NCSC document has no numbered requirements. Auditex gives each requirement a stable
local id, `ce.<theme>.<name>`, and cites the heading path as printed in the document, for example
`E. Requirements by technical control theme > 4. User Access Control > Requirements`. The five
themes are Firewalls, Secure Configuration, Security Update Management, User Access Control and
Malware protection. Every requirement carries one status:

- `automated`: tenant evidence alone decides the whole requirement. None qualifies in v3.3, because
  each requirement also spans devices, other cloud services or organisational practice.
- `partial`: tenant evidence covers part of the requirement. A rule can show a gap, and the requirement
  then fails. A partial requirement never reads `pass`: a clean result is recorded as not assessed with
  the evidence counts.
- `manual`: the applicant answers and evidences it. Auditex reports no verdict.
- `ce_plus_assessor_test`: the CE+ assessor tests it technically. Auditex reports no verdict and any
  rules listed are supporting evidence only. The catalog names the CE+ test case.
- `provider_responsibility`: for SaaS such as Microsoft 365 and Google Workspace the cloud provider
  typically implements the control (Table 1 in the document), and the applicant holds the contractual
  commitment. Auditex reports no verdict.

Most requirements are device, network or process side, so most are `manual`, `ce_plus_assessor_test`
or `provider_responsibility`. Only user access control and parts of secure configuration have tenant
evidence.

**Mapping confidence.** `_cyber_essentials_confidence` in `configs/control-mappings.json` records, for
each rule and requirement, whether the rule tests the named condition for the audited tenant (`full`,
for example `ca.mfa_not_enforced` for MFA on cloud services) or a proxy or subset (`partial`, for
example MFA registration, or Intune noncompliance for update management). A mapping with no declared
confidence is read as `partial`, and a test requires every shipped mapping to declare one.

**Report section.** `baseline_alignment.frameworks.cyber_essentials` lists every catalogued
requirement in catalog order, including those no rule maps to, so none is omitted. Each row has
`control_id`, `title`, `theme`, `requirement_status`, `status`, `citation`, `evidence_limits`,
`rule_ids`, `rule_statuses` (each with the rule's `confidence`), `evidence` (counts of rules mapped,
evaluated, passed, failed, accepted and not assessed, plus open findings), `open_finding_count`,
`finding_ids`, and `ce_plus_test` where the document or test specification names one.

- `status` keeps the four baseline values. `automated` rows take `pass`, `fail`, `accepted_risk` or
  `not_assessed` from their rules, by the same rules as the other frameworks. No requirement is
  `automated` in v3.3, so the shipped section never reads `pass`.
- `partial` rows can read `fail` or `accepted_risk`. When every mapped rule was evaluated and is clean,
  the row reads `not_assessed` with `reason` `partial_requirement_no_gap_found`, and `evidence` shows
  how many rules were evaluated and passed. A partial requirement never reads `pass`. A row whose rules
  were not all evaluated is `not_assessed` too, and the per-rule `reason` says why.
- `manual`, `ce_plus_assessor_test` and `provider_responsibility` rows are always `not_assessed`, with
  `reason` set to `requirement_status:<status>`, whatever their mapped rules report. An unknown
  catalog status is treated the same way. Their `rule_statuses` and `evidence` are supporting detail.
- Requirement ids named by a finding or mapping but missing from the catalog are listed in
  `uncatalogued_requirement_ids`.
- Google Workspace rules reach the section through their findings' `framework_mappings` only. They are
  not in the Microsoft collector map, so a Google requirement shows a rule only when a finding exists,
  and a clean Google run leaves those requirements `not_assessed`.

**Caveat.** Auditex output is evidence for a Cyber Essentials assessor. It is not a Cyber Essentials
assessment, a certificate or a CE+ result. `not_assessed` with `partial_requirement_no_gap_found` means
the mapped rules found no gap in the audited tenant, which is not the same as the requirement being
met. The applicant's own answers and the assessor's tests decide that.

## Limitations

- CIS v7 coverage is partial. Auditex maps 16 of the benchmark's recommendations, chosen where
  its evidence tests the condition directly. A `pass` status means every mapped rule was evaluated (its
  collectors completed and its inputs were present) and raised no finding, not a full CIS audit
  result.
- `consent_policy.user_consent_unrestricted` fires only when users can consent to any app. CIS v7 `5.1.5.1` and SCuBA `MS.AAD.5.2v1` ask for no user consent, so a clean result against them means no unrestricted user consent, not that consent is off.
- Cyber Essentials coverage is partial by design. Six of 30 requirements have tenant evidence behind
  them and none is `automated`, so no Cyber Essentials row can read `pass`. No rule yet checks separate administrator accounts, Defender or other
  anti-malware status, operating system support dates, update age or device lock settings; those stay
  `manual` or `ce_plus_assessor_test` until a collector and rule exist. CE+ is assessed against the v3.2
  test specification, so a future v3.3 specification may change the test-case names.
- MCSB v2 is a preview release, and its ids could change before it is generally available.
- Secure Score control ids are service-defined and change over time. Microsoft does not publish
  a complete list.
- The SCuBA mappings use the policy version suffix current at v1.8.0. When CISA revises a policy
  (`v1` to `v2`), update both the catalog and the mappings.
